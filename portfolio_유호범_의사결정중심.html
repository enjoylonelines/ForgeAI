Project 01 · AI / LLM

ForgeAI — 제조 설비 예지보전 멀티에이전트 RAG 시스템

2026.06개인 프로젝트 PythonLangGraphRAG Rule EngineOllama(qwen2.5:7b) ChromaDBC++ dry-run adapterpytest

프로젝트 목적

제조 설비 센서 로그를 기반으로 고장 위험을 평가하고, SOP 근거를 찾아 조치 계획을 생성·검증하는 예지보전 시스템입니다. 핵심은 LLM이 모든 판단을 대신하는 구조가 아니라, “센서 이상을 탐지하는 일”과 “왜 이상인지·어떻게 대응할지를 설명하는 일”을 서로 다른 문제로 보고, 위험 판단·근거 검색·계획 검증·실행 전 확인을 분리해 추적 가능한 흐름으로 만드는 것이었습니다. 외부 API 없이 온프레미스 LLM만으로 완결하는 폐쇄망 대응을 전제로 설계했습니다.

의사결정 과정

가장 경계한 지점은 “그럴듯한 조치 계획”이 곧 “실행 가능한 조치”처럼 보이는 문제였습니다. 그래서 수ms 안에 결론이 나야 하는 임계값 비교와 고장 모드 분류(TWF·HDF·PWF·OSF)는 결정론적 Rule Engine이 먼저 담당하게 했습니다. AI4I 2020 기준 약 96.6%를 차지하는 정상(SAFE) 케이스는 LLM을 한 번도 호출하지 않고 조기 종료시켜, 처리량이 LLM 지연에 묶이지 않도록 했습니다.

이상이 감지된 경우에만 LLM 에이전트가 복수 센서 조합을 해석하고, SOP RAG가 근거를 검색합니다. 근거가 충분할 때만 조치 계획을 생성하고, 마지막에는 임베딩 코사인 유사도로 각 단계가 실제 SOP 청크에 근거하는지를 검증합니다. 검증을 통과하지 못하면 계획을 그대로 내보내지 않고 재생성하거나 검토 대상으로 보냅니다. C++ control adapter는 dry-run 전용으로 두어, AI 결과가 실제 제어 흐름과 섞이기 전에 한 번 더 걸러지게 했습니다.

의사결정 기반 파이프라인

각 분기는 “이 판단에 언어 이해가 필요한가 / 결정론으로 충분한가”를 기준으로 나뉩니다. 마름모는 판단 분기, 사각형은 처리 단계, 진한 박스는 종료 지점입니다.

처리 단계 판단 분기 종료 지점 보류·재시도
결정론으로 충분한 판단은 Rule Engine·임베딩 유사도가, 언어 이해가 필요한 판단만 LLM이 담당합니다.

구현 근거

  • Rule Engine을 1차 판단 계층으로 두어 센서 기반 위험 판단의 재현성과 감사 가능성을 확보했습니다.
  • SOP RAG는 조치 계획의 근거를 제공하는 역할로 제한해 LLM의 임의 판단 범위를 줄였습니다.
  • LangGraph StateGraph로 위험 평가·근거 검색·계획 생성·검증 단계를 분리하고 조건 분기와 재시도 루프를 선언적으로 표현했습니다.
  • HallucinationValidator가 각 조치 단계를 SOP 청크와 코사인 유사도로 비교해 근거 강도를 수치화합니다.
  • C++ dry-run adapter를 연결해 조치 계획을 실행 전 검증하고, 실제 하드웨어 write는 차단했습니다.

의사결정 과정

채용공고 파싱·브리핑·피드백은 지연이 길어질 수 있는 AI 작업인 반면, 지원 상태·마감일·사용자 데이터는 빠르고 일관되게 관리되어야 하는 도메인 상태입니다. 두 흐름을 같은 요청에 묶으면 AI 지연이 도메인 API 안정성과 사용자 경험을 함께 흔들 수 있다고 판단했습니다. 그래서 Spring Boot는 인증·지원 상태·마감일·도메인 API를, Python AI 서비스는 파싱·브리핑·피드백 파이프라인을 맡도록 분리했습니다. 서비스 경계는 gRPC 계약으로 고정하고, 비동기 처리는 Kafka 이벤트로 흘려보냈으며, 사용자는 SSE로 진행 상태와 결과를 받아 AI 지연을 화면 경험 안에서 관리하도록 했습니다.

  • Spring Boot와 Python AI 서비스를 분리해 도메인 상태와 AI 실행 책임을 나눴습니다.
  • gRPC로 서비스 간 요청·응답 계약을 고정해 경계를 명확히 했습니다.
  • Kafka 비동기 파이프라인 + SSE 스트리밍 응답을 구성했습니다.
  • Career Vault 기반 피드백으로 채용공고와 지원자 이력 근거를 연결했습니다.

지원 직무와의 연결

로컬 AI 개발 엔지니어 직무에서 제가 기여할 수 있는 지점은 단순 모델 호출보다 “판단 흐름을 어떻게 설계하고 검증할 것인가”에 있습니다. 제조 AI는 설비 상태·작업 조건·SOP·조치 이력에 따라 분기가 세분화되어야 하고, 에이전트가 생성한 결과도 환각 여부·SOP 근거·실행 가능성을 기준으로 평가되어야 합니다.

ForgeAI에서는 이 문제를 Rule Engine·SOP RAG·LangGraph·C++ dry-run으로 나누어 작게 검증했고, 무엇을 아직 못 했는지를 빈칸으로 남겨 정직하게 드러냈습니다. Landed에서는 AI 실행 계층과 도메인 상태 계층을 서비스 경계로 분리했고, AlbaFit과 재고관리에서는 실제 업무·협업 흐름에서 누락과 정합성 문제가 생기는 지점을 구조적으로 줄였습니다. 입사 후에는 설비 로그·SOP·조치 이력을 연결하고, 상황별 분기와 평가 지표를 갖춘 로컬 AI 에이전트 구축에 기여하겠습니다.
