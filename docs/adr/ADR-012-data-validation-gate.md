# ADR-012: 데이터 검증 단계 (서빙 전 품질 게이트)

**상태:** 검토중 (설계 확정, 구현 미완)

---

## 맥락

"Garbage In, Garbage Out." 센서 데이터의 품질 오류가 모델 예측에 그대로 전달되면  
잘못된 CRITICAL 경보 또는 실제 고장을 놓치는 미탐이 발생한다.  
모델 자체의 정확도와 무관하게 입력 데이터 오류가 시스템 신뢰성을 훼손한다.

현재 FastAPI `/analyze` 엔드포인트는 Pydantic 스키마 타입 검증만 수행하고  
센서값의 물리적 의미(범위·결측·이상치) 검증은 없다.

---

## 고려한 대안

### 대안 A: Pydantic 스키마 타입 검증만 유지

- 현재 구현 상태
- **문제점:** `air_temp: float` 검증은 통과하지만 `-999.0`이나 `0.0` 같은 센서 고장값이 그대로 통과됨

### 대안 B: rule engine 내부 검증 포함

- `assess_risk()` 안에서 범위 검사 병행
- **문제점:** 이상 탐지 로직과 데이터 품질 검증이 섞인다.  
  "센서가 이상한가"와 "데이터가 오염됐는가"는 다른 질문이다.

### 대안 C: 서빙 파이프라인 진입 전 별도 검증 단계 — 채택

- 예측 파이프라인에 진입하기 전 독립된 검증 레이어를 둔다
- 검증 실패 → 파이프라인 진입 차단 + 오류 로그 기록
- 검증 경고 → 예측은 계속하되 플래그 포함한 결과 반환

---

## 결정

FastAPI 엔드포인트와 rule engine 사이에 **데이터 검증 게이트**를 삽입한다:

### 검증 항목 및 기준

| 검증 유형 | 대상 필드 | 기준 | 실패 시 |
|-----------|----------|------|---------|
| 스키마 완결성 | 5개 센서 필드 전체 | null/누락 없음 | 400 오류, 파이프라인 차단 |
| 범위 검사 (hard) | `rpm` | 0 ≤ rpm ≤ 3500 | 400 오류, 파이프라인 차단 |
| 범위 검사 (hard) | `tool_wear` | 0 ≤ tool_wear ≤ 300 | 400 오류, 파이프라인 차단 |
| 범위 검사 (hard) | `air_temp` | 295 ≤ temp ≤ 320 (K) | 400 오류, 파이프라인 차단 |
| 범위 검사 (soft) | `torque` | 3σ 이탈 시 | 경고 플래그, 예측 계속 |
| 물리적 일관성 | `process_temp ≥ air_temp` | process_temp − air_temp ≥ 0 | 경고 플래그, 예측 계속 |

## 이유 (인과)

데이터 검증을 파이프라인 상류(upstream)에서 거르는 이유는 세 가지다:

1. **조기 실패(fail fast):** 오염된 데이터로 LLM을 호출하면 불필요한 비용·지연이 발생한다.
2. **책임 분리:** "예측기가 틀린 것인가, 입력이 잘못된 것인가"를 구분할 수 있어야 디버깅이 가능하다.
3. **모니터링 기반:** 검증 실패 로그를 누적하면 센서 고장 패턴과 데이터 품질 추세를 추적할 수 있다.

---

## 포기한 것 / 트레이드오프

엄격한 hard 검증은 경계값 근처의 실제 이상 데이터를 차단할 위험이 있다.  
예: 극단 부하 상황에서 rpm이 정상 범위를 살짝 벗어나는 경우.  
이를 보완하기 위해 hard/soft 2단계 검증을 두고, soft 경우는 예측을 허용하되 플래그를 남긴다.
