# ADR-005: 예측은 고전 ML / LLM은 RCA·운영 레이어 분리

**상태:** 채택

---

## 맥락

"LLM을 쓴다"는 결정은 "LLM이 모든 것을 잘 한다"가 아니라  
"이 특정 판단에 언어 이해가 필요한가"에 대한 분석에서 나와야 한다.  
초기 설계에서 PerceptionAgent 프롬프트에 TWF/HDF/PWF/OSF 판별 기준이 들어있었다.  
이는 LLM이 분류를 담당하게 유도하는 구조였고, 결정론적이어야 할 판단이 확률론적 출력에 의존하는 문제였다.

또한 "XGBoost로 충분하지 않은가"라는 질문에 구체적으로 답할 수 없으면  
LLM 에이전트 도입의 정당성이 없다.

---

## 고려한 대안

### 대안 A: LLM이 전 단계 담당 (분류 + RCA + 계획)

- **장점:** 단일 인터페이스, 파이프라인 단순
- **단점:**
  - 수ms에 결론이 나야 할 임계값 비교를 LLM(수초)에 맡기면 실시간 처리 불가
  - LLM 분류 결과가 rule engine 조건식과 다를 때 어느 쪽이 맞는지 알 수 없음
  - 감사(audit) 불가 — "왜 CRITICAL로 분류됐는가"를 LLM 응답에서 재구성해야 함

### 대안 B: 정형 ML만 (LLM 없음)

- **장점:** 빠름, 감사 가능, 운영 단순
- **단점:**
  - 고장 모드별 조치계획 생성 불가 (SOP를 이해하고 상황에 맞게 절차를 생성하는 것은 정형 ML로 불가)
  - RNF 같은 패턴 없는 고장에 대한 설명 생성 불가
  - 운전자에게 "왜 위험한가"를 자연어로 설명하는 기능 없음

### 대안 C: 역할 분리 — 채택

```
결정론적 판단  → rule engine / 정형 ML
언어 이해 필요 → LLM 에이전트
```

---

## 결정

다음 원칙으로 각 컴포넌트의 역할을 고정한다:

| 판단 유형 | 담당 | 근거 |
|-----------|------|------|
| 센서 임계값 초과 여부 | rule engine | 산술 비교, 결정론적 |
| 고장 모드 분류 (TWF/HDF/PWF/OSF) | rule engine (AI4I 조건식) | 도메인 조건식이 명확히 존재 |
| 이상 탐지 확률 추정 | 정형 ML (XGBoost/RF) | PR-AUC 0.830, 감사 가능 |
| 복수 센서 조합 해석 | LLM (PerceptionAgent) | 조합 패턴에 자연어 표현 필요 |
| SOP 문서 기반 조치계획 생성 | LLM (ActionPlanAgent) | 문서 이해 + 상황 맞춤 절차 생성 |
| 조치계획 근거 검증 | 임베딩 코사인 유사도 | 수치 계산, LLM 불필요 |

**수정 내역:** PerceptionAgent 프롬프트에서 TWF/HDF/PWF/OSF 판별 기준 제거.  
LLM은 "센서 값이 얼마나 벗어났는가, 어떤 조합으로 이상인가"만 분석하고,  
failure_type 레이블은 rule engine이 단독 결정한다.

---

## 이유 (인과)

분리의 핵심 이유는 두 가지다:

1. **감사 가능성:** rule engine의 분류 결과는 조건식으로 역추적 가능하다. LLM 분류는 재현이 안 된다.
2. **속도:** rule engine은 수ms, LLM은 수초다. 96.6%의 SAFE 케이스를 모두 LLM에 보내면 처리량이 100배 이상 줄어든다.

---

## 포기한 것 / 트레이드오프

rule engine 조건식이 AI4I 2020 기준으로 작성되어 있어 다른 설비 타입에는 재작성이 필요하다.  
LLM이 조건식을 동적으로 결정하는 유연성을 포기했다.  
보완: rule engine 임계값을 설정 파일(`core/config.py` + `.env`)로 분리해 재배포 없이 조정 가능하게 한다.

---

## 결과 / 검증

**달성된 결과:**
- SAFE early exit으로 AI4I 기준 96.6%의 row에서 LLM 4회 호출 생략
- e2e 테스트 26개에서 rule engine 분류 결과와 LLM 해석 출력이 일관성 확인됨
- `docs/decisions.md`의 버그 ①(HDF/PWF/OSF early exit 오분류) 수정 — rule engine 역할 경계가 불명확해 생긴 버그
